STAGE 11 — ADMINISTRATION, AUDIT & SYSTEM MANAGEMENT
============================================================

PROJECT:
Hospital Health Data Management, Reporting and Analysis System

STAGE:
11 of 14

TITLE:
Administration, Audit & System Management

============================================================
1. STAGE OBJECTIVE
============================================================

Stage 11 implements the administrative management layer of the
Hospital Health Data Management, Reporting and Analysis System.

The ADMIN role becomes responsible for managing:

1. System users
2. User roles and account status
3. Administrative password management
4. Audit logs
5. Administrative system information/configuration
6. Administrative notification visibility where appropriate

Stage 11 must provide a professional Admin experience consistent
with the UI/UX established in Stages 05–10.

The objective is to give the ADMIN role a controlled interface for
managing the application itself without exposing direct database
operations or unsafe system configuration.

Stage 11 must preserve all functionality implemented in
Stages 01–10.

4. ADMIN ACCESS MODEL
============================================================

All Stage 11 administrative APIs must require:

1. Authentication
2. ADMIN role

A non-admin authenticated user must receive:

HTTP 403 Forbidden

Unauthenticated users must receive:

HTTP 401 Unauthorized


Frontend routes must also be protected using the existing
RequireAuth / RequireRole architecture.

ADMIN-only pages include:

/app/admin
/app/admin/users
/app/admin/audit-logs
/app/admin/system


If an ADMIN route is opened by another role:

- Do not render administrative content.
- Use the existing unauthorized/forbidden behavior.

Do not rely on frontend protection alone.

Every administrative API must enforce ADMIN authorization
on the server.

------------------------------------------------------------
5.2 CREATE USER
------------------------------------------------------------

ADMIN can create a new user.

Required fields:

- Full name
- Email
- Role
- Initial password

Optional fields should NOT be invented unless already supported
by the existing users schema.

Allowed roles:

ADMIN
DATA_ENTRY
REPORTING
MANAGER


Email must be unique.

Duplicate email:

HTTP 409 Conflict


Password must never be stored as plain text.

Use the existing password hashing mechanism established in Stage 04.

The API must hash the password before persistence.

The frontend must never display or retrieve an existing user's
password/hash.

------------------------------------------------------------
5.3 EDIT USER
------------------------------------------------------------

ADMIN can update:

- Full name
- Email
- Primary role
- Account status

Email uniqueness must remain enforced.

Changing a user's role must be auditable.

Changing account status must be auditable.

Do not allow editing immutable database identifiers.

------------------------------------------------------------
5.4 ACTIVATE / DEACTIVATE USER
------------------------------------------------------------

ADMIN can activate or deactivate accounts.

Deactivation must prevent the user from authenticating.

An already-authenticated inactive user must not continue using
protected APIs indefinitely.

Existing authentication/session checks must respect the user's
current account status.

If the existing JWT/session architecture needs an explicit
database status check for this rule, implement the minimum change
required.

Do not create a new authentication architecture.

============================================================
6. LAST ADMIN PROTECTION
============================================================

The system must never allow the final usable ADMIN account to
be removed from administrative control.

The following operations must be blocked when they would result
in zero active administrators:

- Deactivating the last active ADMIN
- Changing the role of the last active ADMIN to another role

Return:

HTTP 409 Conflict

Use a clear message such as:

"At least one active administrator account must remain."

This rule must be enforced server-side.

The frontend may warn the administrator before submitting the
operation, but the backend remains authoritative.

Deleting users is NOT supported in Stage 11.

Use deactivation instead.

============================================================
7. ADMIN PASSWORD MANAGEMENT
============================================================

Stage 11 supports administrative password management.

ADMIN may reset/change another user's password.

This operation must:

1. Accept a new password
2. Hash the password using the existing hashing mechanism
3. Replace the stored password hash
4. Revoke that user's active refresh sessions
5. Record an audit event

The user's existing access tokens should become unusable according
to the existing authentication/session architecture as far as
practical.

Do not display the generated or existing password after submission.

The Admin UI should clearly communicate:

"Password changed successfully."

Do not implement:

- Email password reset
- SMS password reset
- Password recovery links
- OTP password recovery

Those are outside Stage 11.

============================================================
8. SELF-ACCOUNT SAFETY
============================================================

An administrator may edit their own profile where supported.

However, the system must prevent an administrator from accidentally
removing their own last administrative access.

Examples:

If there is only one active ADMIN:

- Cannot change own role away from ADMIN.
- Cannot deactivate own account.

If multiple active ADMIN accounts exist:

- These restrictions may be relaxed according to the same
  last-admin rule.

The server must make the final decision.

28. USER STATUS AND SESSION BEHAVIOR
============================================================

When an account is deactivated:

1. Authentication must be blocked.
2. Active refresh sessions should be revoked.
3. Existing protected requests must respect account status.
4. The action must be audited.

When a password is changed:

1. Password hash is replaced.
2. Refresh sessions are revoked.
3. The action is audited.

The system must not leave long-lived refresh sessions active after
a security-sensitive account change.

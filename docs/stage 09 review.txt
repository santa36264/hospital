1. IMPLEMENTATION SUMMARY
============================================================

Stage 09 implements the Custom Report Builder and export layer.

Users (REPORTING, ADMIN) can now:
- Select a dataset, one or more indicators, and one or more periods
- Preview an indicator-by-period matrix using APPROVED data only
- Export as PDF (server-generated via PDFKit)
- Export as Excel (server-generated via ExcelJS)
- Print via browser print dialog

Key design decisions:
- One shared buildReportData() generates the normalised matrix
  structure used identically by Preview, PDF, and Excel — no
  divergence between formats.
- Single bulk JOIN query (no N+1) fetches all matrix cells.
- Periods are ordered chronologically by the repository (ORDER BY
  start_date ASC) regardless of the order the client sends them.
- Missing/unapproved cells remain null — never converted to zero.
- PDF and Excel are server-generated from DB data; the client
  cannot inject arbitrary values into exports.
- CUSTOM_REPORT extends the existing report_history mechanism
  via a new migration (enum value added).

All Stage 03–08 functionality is preserved unchanged.
No Stage 10+ functionality was implemented.

4. API ENDPOINTS (Stage 09 new)
============================================================

All require authentication (401) and REPORTING or ADMIN role (403).

POST /api/v1/reports/custom/preview
  Body: { dataset_id, indicator_ids[], reporting_period_ids[] }
  Returns: { dataset, indicators[], periods[], matrix{}, generatedAt }
  422 if any param is missing, empty, or exceeds limits.
  404 if dataset not found.
  422 if any indicator doesn't belong to dataset.
  422 if any period not found.
  Data in matrix is null where no approved submission exists.

POST /api/v1/reports/custom/export/pdf
  Same body as preview. Re-queries DB — never trusts client data.
  Returns: application/pdf stream as attachment.
  Same validation as preview.

POST /api/v1/reports/custom/export/excel
  Same body as preview. Re-queries DB.
  Returns: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
  stream as attachment.

6. CUSTOM REPORT QUERY ARCHITECTURE
============================================================

One normalised pipeline shared by all output formats:

  POST /preview or /export/*
       │
       ▼
  customReportController.parseBody()
       │
       ▼
  customReportService.buildReportData()
    ├─ validateInput() — size limits + required checks
    ├─ customReportRepository.loadSelections()
    │   ├─ db('datasets').where(id)
    │   ├─ db('indicators').whereIn(id).where(dataset_id) — security
    │   └─ db('reporting_periods').whereIn(id).orderBy(start_date)
    ├─ Verify all indicator IDs found (cross-dataset → 422)
    ├─ Verify all period IDs found
    ├─ customReportRepository.fetchMatrixValues()  — SINGLE JOIN QUERY
    │   SELECT indicator_id, period_id, value
    │   FROM data_values
    │   JOIN submissions ON submissions.id = data_values.submission_id
    │   WHERE indicator_id IN (...)
    │   AND period_id IN (...)
    │   AND dataset_id = X
    │   AND status = 'APPROVED'
    ├─ Build lookup map: { indicatorId: { periodId: rawValue } }
    └─ Build matrix: { indicatorId: { periodId: formattedValue|null } }
           └─ valueFormatter.formatIndicatorValue() per cell
       │
       ▼
  { dataset, indicators, periods, matrix, generatedAt }
       │
       ├─ JSON response (preview)
       ├─ pdfReportService.generatePDF() → stream
       └─ excelReportService.generateExcel() → stream

============================================================
7. APPROVED-DATA RULES
============================================================

1. fetchMatrixValues filters: WHERE submissions.status = 'APPROVED'
2. DRAFT / SUBMITTED / UNDER_REVIEW / RETURNED are excluded.
3. Missing cells (no approved submission) are null in the matrix.
4. null is rendered as "N/A" in preview UI, PDF, and Excel.
5. null is NEVER converted to 0 or any other default value.
6. The server rebuilds report data from the DB for every export.
   The client cannot inject values.

13. PROBLEMS ENCOUNTERED AND FIXED
============================================================

PROBLEM 1: Test setup called /submit before /patch (saving values).
  The submission had required indicators. Submit failed with 422
  "field is required", so the submission was never APPROVED.
  The subsequent review/approve calls also failed cascading.

FIX: Reordered test setup to: create DRAFT → PATCH (save values)
  → submit → start-review → approve. All setup steps now succeed.

PROBLEM 2: ApiPostRaw in the test script created a new
  CookieContainer inside a foreach loop, overwriting itself
  with each cookie iteration — resulting in an unauthenticated
  request (no cookies sent).

FIX: Create the CookieContainer once before the loop, then
  add all cookies to it in the loop. PDF/Excel export tests
  now correctly authenticate and receive binary responses.

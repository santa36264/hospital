UI/UX RECONSTRUCTION SPECIFICATION
==================================

Project:
Hospital Health Data Management, Reporting and Analysis System

Document:
ui.txt

Purpose:
Complete frontend UI/UX reconstruction of the existing Hospital Health
Data Management, Reporting and Analysis System.

This document defines the visual design, information architecture,
navigation, page layouts, reusable components, responsive behavior,
accessibility, and interaction standards for the ENTIRE frontend.

This is NOT an icon replacement task.

This is NOT a color-change task.

This is NOT a small styling improvement.

The existing frontend must be reconstructed into a coherent,
professional, production-quality hospital health-data application.

============================================================
1. CORE OBJECTIVE
============================================================

The final frontend must feel like ONE complete application.

Every page must share:

- the same design system
- the same spacing system
- the same typography
- the same button styles
- the same form styles
- the same table styles
- the same status styles
- the same navigation system
- the same icon system
- the same interaction patterns
- the same responsive behavior

Do not design every page independently.

Create reusable components and use them consistently.

The application should feel:

- professional
- clean
- calm
- trustworthy
- healthcare appropriate
- data-oriented
- practical
- modern
- accessible

It should NOT feel like:

- a generic CRUD admin template
- a student project
- a dashboard template with random cards
- a collection of unrelated pages
- a UI made entirely from white cards
- an icon showcase
- a decorative design

============================================================
2. CRITICAL IMPLEMENTATION RULE
============================================================

EVERY VISIBLE NAVIGATION LINK MUST WORK.

Do not add a sidebar link simply because it looks good.

For every navigation item:

1. The route must exist.
2. The route must load successfully.
3. The page must be implemented.
4. The page must use real application data where applicable.
5. The page must respect RBAC.
6. The page must not be a placeholder.
7. The page must not show "Coming Soon".
8. The page must not show fake data.
9. The page must not lead to a broken route.
10. The active navigation state must work.

If a required page already exists:
- redesign it.

If the page exists but is incomplete:
- complete it.

If a navigation item has no valid destination:
- implement the required page before adding the link.

Do not leave dead navigation.

============================================================
3. DO NOT REWRITE THE BACKEND
============================================================

This is a frontend reconstruction.

Preserve:

- Node.js
- Express
- MySQL/MariaDB
- Knex
- existing REST APIs
- JWT authentication
- refresh sessions
- RBAC
- submission workflow
- review workflow
- reports
- custom reports
- exports
- analytics
- notifications
- audit logs
- existing business rules
- existing security rules

Only modify backend/API behavior when absolutely necessary to support
an existing frontend requirement.

Do not create duplicate backend systems.

Use a restrained professional healthcare-oriented palette.

Primary:
- deep navy/blue

Secondary:
- muted blue/slate

Background:
- soft neutral/light gray

Surface:
- white

Text:
- dark neutral

Muted text:
- slate/gray

Semantic:

- green

Warning:
- amber

Danger:
- red

Information:
- blue

Status colors must be consistent throughout the application.

Do not rely only on color to communicate status.

============================================================
6. TYPOGRAPHY
============================================================

Establish a consistent typography hierarchy.

Use clear differences between:

- page title
- page subtitle
- section heading
- card heading
- table heading
- body text
- supporting text
- labels
- status text

Avoid:

- oversized headings
- excessive bold text
- tiny body text
- inconsistent font sizes
- random capitalization

Page titles should be prominent but not excessive.

============================================================
7. SPACING SYSTEM
============================================================

Do not randomly choose padding/margin on every page.

Use a consistent spacing scale.

Page layout should have:

- consistent outer padding
- consistent section spacing
- consistent card padding
- consistent table row height
- consistent form spacing

Do not create enormous empty areas unnecessarily.

Do not compress content so tightly that the interface becomes difficult
to scan.

The amount of whitespace must support hierarchy and readability.

============================================================
8. CARDS
============================================================

Do not put every piece of information inside a card.

Cards should be used when they create meaningful grouping.

Good uses:

- KPI
- important summary
- grouped information
- focused action area
- chart
- form section

Bad use:

A page consisting of 8–12 identical white boxes simply because cards
look modern.

Cards should have:

- consistent radius
- subtle border/shadow
- consistent padding
- clear hierarchy

Do not overuse shadows.

- skeletons

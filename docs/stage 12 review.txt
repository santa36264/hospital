============================================================
1. SECURITY/BUSINESS-RULE ISSUES DISCOVERED
============================================================

- Pagination inputs were not validated/clamped (invalid or
  oversized page/pageSize could produce SQL errors or excessive
  reads) on /admin/users and /admin/audit-logs.
- Admin user deactivate + refresh-session revocation + audit were
  NOT wrapped in a transaction; a failure could leave sessions
  active after deactivation/password change.
- No HTTP security headers set (X-Content-Type-Options,
  X-Frame-Options, Referrer-Policy, Cache-Control, etc.).
- Password length rule was inline; centralized for consistency.
- Audit-log export of hashes/tokens: verified none exposed.
- Object-level checks (submission ownership, notification
  ownership) were verified as present and re-tested.

============================================================
5. SECURITY/VALIDATION IMPROVEMENTS
============================================================

- normalizePagination clamps page>=1 and pageSize to 1..100 on
  /admin/users and /admin/audit-logs; invalid values safely
  normalized (no NaN SQL).
- Centralized password policy (min 12, non-blank) shared by admin
  user flows.
- Admin password change and deactivation now run inside
  db.transaction covering user update (where applicable),
  refresh-session revocation, and the audit record atomically.
- securityHeaders middleware applies X-Content-Type-Options,
  X-Frame-Options, Referrer-Policy, X-XSS-Protection,
  Cross-Origin-Resource-Policy, and Cache-Control: no-store to
  every response.
- Verified no SQL error leakage in 500 responses (message masked
  in production; errors are consistent JSON).

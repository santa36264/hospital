============================================================
STAGE 05 — DATASET, INDICATOR & REPORTING PERIOD MANAGEMENT REVIEW
============================================================

PROJECT: Hospital Health Data Management, Reporting and Analysis System
REVIEW TYPE: Stage 05 implementation review (no Stage 06 features)

============================================================
1. WHAT WAS IMPLEMENTED
============================================================

- Admin Dataset management (list/view/create/update/activate/
  deactivate) via API + Tailwind UI at /app/admin/datasets.
- Admin Indicator management (list/filter/search/create/update/
  activate/deactivate) via API + Tailwind UI at
  /app/admin/indicators.
- Admin Reporting Period management (list/filter/search/create/
  update/open/close) via API + Tailwind UI at
  /app/admin/reporting-periods.
- Backend validation, duplicate protection, OPEN/CLOSED and
  ACTIVE/INACTIVE status rules, admin-only authorization on all
  configuration endpoints.
- Audit events for all configuration actions (into existing
  audit_logs).

============================================================
2. DATASET IMPLEMENTATION
============================================================

Repository: server/src/repositories/datasetRepository.js
Service: server/src/services/datasetService.js
Controller: server/src/controllers/datasetController.js
Routes: server/src/routes/datasetsRoutes.js

- code required, normalized (trim, uppercase, spaces to underscore),
  unique (409 on duplicate).
- name required, trimmed. description optional.
- status ACTIVE/INACTIVE toggle via PATCH /:id/status.
- No hard delete. Deactivated datasets remain historically.

============================================================
3. INDICATOR IMPLEMENTATION
============================================================

Repository/Service/Controller/Routes:
indicatorRepository.js / indicatorService.js /
indicatorController.js / indicatorsRoutes.js

- belongs to a dataset (existence verified; 422 otherwise).
- code unique within dataset (409 on duplicate).
- data_type enum (existing Stage 03): numeric, decimal, text,
  date, yes/no, percentage. The UI presents these consistently
  (YES/NO labeled BOOLEAN).
- min_value/max_value/precision only meaningful for numeric-like
  types; stored as NULL for text/date/yes-no types.
- percentage defaults to 0–100 when not explicitly configured.
- min <= max enforced; precision integer 0–10.
- No hard delete.

============================================================
4. REPORTING-PERIOD IMPLEMENTATION
============================================================

Repository/Service/Controller/Routes:
reportingPeriodRepository.js / reportingPeriodService.js /
reportingPeriodController.js / reportingPeriodsRoutes.js

- period_type: MONTHLY/QUARTERLY/YEARLY/CUSTOM (new column in
  migration 003).
- label, start_date, end_date required; end >= start enforced.
- Lifecycle: OPEN -> CLOSED. Reopening a CLOSED period is
  rejected (409) through ordinary operation; auditable path is a
  later-stage concern.
- No hard delete. Closed-period data remains historical.

============================================================
5. DATABASE CHANGES
============================================================

Migration 003_reporting_periods_type: added
reporting_periods.period_type ENUM('MONTHLY','QUARTERLY','YEARLY',
'CUSTOM') NOT NULL DEFAULT 'MONTHLY'. Additive only. No tables
dropped, no data destroyed. Stage 03 schema otherwise unchanged;
datasets/indicators already contained required columns, so no
schema changes were needed there.

============================================================
7. AUTHORIZATION
============================================================

All configuration routes use requireAuth + requireRole('ADMIN').
Verified: Data Entry / Reporting / Manager receive 403 on
mutations; anonymous receives 401. Backend enforcement; frontend
hiding is not the security boundary.

============================================================
8. VALIDATION
============================================================

- Dataset: missing/blank code/name rejected (422); duplicate code
  409; invalid status rejected.
- Indicator: missing dataset/code/name/type rejected; invalid
  dataset 422; invalid data_type 422; min>max rejected; invalid
  precision rejected; duplicate (dataset_id, code) 409.
- Period: missing label/type/dates rejected; invalid period_type
  422; end before start 422; closed-period reopen 409.
- Backend is authoritative; DB constraints are the final backstop.

============================================================
9. STATUS TRANSITIONS
============================================================

- Dataset: ACTIVE <-> INACTIVE (toggle).
- Indicator: ACTIVE <-> INACTIVE (toggle).
- Period: OPEN -> CLOSED only (no ordinary reopen button or API
  path).

14. PROBLEMS ENCOUNTERED
============================================================

- knex whereILike is not valid for MySQL — replaced with LIKE.
- `precision` is a reserved word in MariaDB SQL — quoted in
  ad-hoc queries; service layer unaffected.
- MariaDB auto-defaulting of TIMESTAMP columns observed in Stage 04
  remains avoided (new migration uses enum + defaults only).

============================================================
11. DATABASE DESIGN PRINCIPLE
============================================================

The database must represent the business requirements from Stage 01.

The initial core domain includes:

- Users
- Roles
- Datasets
- Indicators
- Reporting Periods
- Submissions
- Data Values
- Submission History
- Notifications
- Audit Logs

Additional supporting tables may be introduced when technically
necessary.

Do not add unrelated hospital-management entities such as:

- Patients
- Doctors
- Pharmacy
- Billing
- Appointments
- Laboratory
- Insurance

unless explicitly required by Stage 01.

This project is a health-data management/reporting/analysis system,
not a complete hospital information system.

============================================================
12. ROLE DESIGN
============================================================

The initial system has exactly four primary roles:

ADMIN
DATA_ENTRY
REPORTING
MANAGER

Each user has ONE primary role.

Multi-role users are out of scope.

The database must support role-based authorization.

============================================================
13. USERS
============================================================

The users table must support at minimum:

- unique identifier
- name
- email/username as appropriate
- password hash
- role reference
- account status
- created timestamp
- updated timestamp

Do not store plaintext passwords.

Authentication implementation belongs to Stage 04.

============================================================
14. ROLES
============================================================

The roles table must support the four initial roles:

ADMIN
DATA_ENTRY
REPORTING
MANAGER

Role values should be controlled and unique.

The implementation may use:

- role table + foreign key

rather than hardcoding role names throughout database queries.

============================================================
15. DATASETS
============================================================

A dataset represents a collection of health indicators.

Dataset must support at minimum:

- identifier
- name
- code where appropriate
- description
- active/inactive status
- created timestamp
- updated timestamp

Dataset deactivation must preserve historical information.

Inactive datasets must not accept new data.

============================================================
16. INDICATORS
============================================================

An indicator belongs to a dataset.

Indicator must support configuration needed by Stage 01:

- identifier
- dataset reference
- name
- code
- description
- data type
- required flag
- active/inactive status
- minimum value where applicable
- maximum value where applicable
- precision where applicable
- created timestamp
- updated timestamp

Initial supported conceptual data types:

- numeric
- decimal
- text
- date
- yes/no
- percentage

Percentage indicators must support the default validation range:

0–100

Numeric indicators must support configurable validation rules.

Do not hardcode all indicator limits into application code.

============================================================
17. REPORTING PERIODS
============================================================

Reporting periods represent periods in which health data is entered.

A reporting period must support:

- identifier
- period name/label
- start date where appropriate
- end date where appropriate
- status
- created timestamp
- updated timestamp

Initial period statuses:

OPEN
CLOSED

Closed periods must not accept ordinary new data.

Reopening a closed period is exceptional and must be auditable.

============================================================
18. SUBMISSIONS
============================================================

A submission represents:

ONE Dataset
+
ONE Reporting Period
+
ONE Data Entry Owner

A submission must support:

- identifier
- dataset reference
- reporting period reference
- owner/user reference
- status
- submitted timestamp where applicable
- reviewed timestamp where applicable
- approved timestamp where applicable
- returned timestamp where applicable
- created timestamp
- updated timestamp

Persistent statuses are exactly:

DRAFT
SUBMITTED
UNDER_REVIEW
RETURNED
APPROVED

Do NOT create a persistent RESUBMITTED status.

Resubmission means:

RETURNED -> SUBMITTED

============================================================
19. SUBMISSION UNIQUENESS
============================================================

There must be only ONE active submission for:

Dataset + Reporting Period

The database must enforce this requirement as far as technically
possible.

The implementation must prevent duplicate active submissions caused
by concurrent requests.

============================================================
20. DATA VALUES
============================================================

Submission data must be stored separately from the submission
metadata.

A data value belongs to:

Submission
+
Indicator

The design must allow an indicator to store the configured data type.

The database design must support validation and retrieval of
indicator values for reports and analysis.

Do not create one database column for every indicator.

Indicators are dynamic configuration records.

Therefore the design must support dynamic indicators.

============================================================
21. SUBMISSION HISTORY
============================================================

Submission workflow history must be preserved.

The system must be able to determine:

- who submitted
- who started review
- who returned
- who resubmitted
- who approved
- when each action occurred
- return reason where applicable

The history design must preserve the original submission record.

Returned submissions are corrected and resubmitted rather than
creating a new submission.

============================================================
22. APPROVED DATA AMENDMENTS
============================================================

Stage 01 requires controlled amendments for approved data.

Stage 03 must provide the database architecture needed to preserve
original approved information and record later amendments.

The exact amendment workflow may be finalized in a later stage.

Do not allow a normal Data Entry update operation to overwrite
approved data directly.

============================================================
23. NOTIFICATIONS
============================================================

Notifications are persistent database records.

The design must support:

- recipient
- notification type
- message
- read/unread state
- created timestamp
- read timestamp where applicable

Notifications will be used by later stages.

Do not implement the complete notification system yet.

============================================================
24. AUDIT LOGS
============================================================

Audit logs are separate from application logs.

Audit records must support:

- user
- action
- resource type
- resource identifier
- timestamp
- old values where required
- new values where required
- useful metadata where appropriate

Audit logs are append-only from the application perspective.

Ordinary users cannot edit/delete audit logs.

Audit-log access is ADMIN-ONLY.

Reporting users use submission workflow history rather than general
audit-log access.

============================================================
25. DATABASE RELATIONSHIP DIRECTION
============================================================

The core relationship direction should be:

Role
  |
  +---- Users

Dataset
  |
  +---- Indicators

Dataset
  |
  +---- Submissions
              |
              +---- Reporting Period
              |
              +---- User/Owner
              |
              +---- Data Values
              |
              +---- Submission History

User
  |
  +---- Notifications

User
  |
  +---- Audit Logs


A submission belongs to one dataset and one reporting period.

An indicator belongs to one dataset.

A data value belongs to one submission and one indicator.

============================================================
26. DATABASE INTEGRITY
============================================================

Use appropriate:

- Primary keys
- Foreign keys
- Unique constraints
- NOT NULL constraints
- Indexes
- Appropriate data types
- Timestamp fields

Foreign-key relationships must preserve referential integrity.

Do not use destructive cascading deletes where they could destroy
historical health data.

Prefer preserving historical records.

============================================================
27. DATABASE MIGRATION / SCHEMA MANAGEMENT
============================================================

The project must have a reproducible database setup.

Use an appropriate MySQL migration/schema-management approach.

The exact Node.js database library may be selected during
implementation.

Candidates may include:

- Prisma
- Sequelize
- Knex
- mysql2 with a controlled migration solution

Select ONE approach.

Do not install multiple ORMs/query builders unnecessarily.

The selected solution must work well with:

- MySQL
- Node.js
- migrations
- relationships
- transactions
- parameterized queries
- maintainability

Document the selected database technology in the Stage 03 review.

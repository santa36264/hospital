1. STAGE 01 REVIEW SUMMARY
============================================================

The Stage 01 document is comprehensive and generally well structured. It clearly states:

- The system is a SINGLE-HOSPITAL health data management, reporting, and analysis system.
- It is NOT a multi-hospital or full EMR/patient-management system.
- The technology stack (React client/, Node.js + Express server/, MySQL, JWT auth, REST API).
- Four roles (Admin, Data Entry, Reporting, Manager) and their responsibilities.
- Core concepts: Dataset, Indicator, Reporting Period, Data Entry, Submission.
- Draft -> Submission -> Review -> Approve/Return -> Correct -> Resubmit -> Approve workflow.
- Validation, business rules (BR-001..BR-022), audit logs, notifications, dashboards,
  analysis, exports, NFRs, out-of-scope list, proposed entities, and stage mapping.

Overall the document is internally CONSISTENT on the major points and provides a strong
foundation. However, several requirements are ambiguous or conflicting (detailed in
sections 4 and 5 below) and must be resolved before Stage 02/Stage 03.

4. AMBIGUOUS REQUIREMENTS
============================================================

A-01  Submission granularity (IMPORTANT)
      It is not defined whether a submission is per dataset+period, per dataset+period+user,
      or a user-chosen bundle. The duplicate-prevention rule (Section 15) references
      "relevant submission/data-entry context" but does not define it.
      Impact: uniqueness constraints and workflow ownership cannot be designed.

A-02  Data ownership chain diagram vs. text (Section 8)
      Section 8 text says a data entry stores the value for an indicator during a specific
      reporting period, but the diagram shows Data Entry connected to Dataset, Reporting
      Period, and Submission — and does NOT show the link to Indicator.
      The chain Dataset -> Indicator -> Reporting Period -> Data Entry -> Submission ->
      Review -> Approval -> Report -> Analysis is implied in text but not diagrammed.

A-03  DRAFT as a submission status (Section 13)
      It is unclear whether a Submission record is created at draft time or only at
      submission time. "DRAFT" is listed as a submission status, implying a submission
      row may exist while still a draft. The relationship between submissions and
      data_values during draft editing is undefined.

A-04  Transition SUBMITTED -> UNDER REVIEW (Section 13)
      Who/what moves a submission from SUBMITTED to UNDER REVIEW? Is it automatic,
      or does a Reporting user explicitly claim/pick it up? Not defined.

A-05  RESUBMITTED status not described (Section 13)
      The workflow diagram includes RESUBMITTED -> REVIEW -> APPROVED, but the status
      descriptions below the diagram only cover DRAFT, SUBMITTED, UNDER REVIEW,
      RETURNED, APPROVED. Is RESUBMITTED a distinct persistent status, or does a
      correction move the submission back to SUBMITTED/UNDER REVIEW? Also, the diagram
      uses "REVIEW" while the status name elsewhere is "UNDER REVIEW".

A-06  Correction scope after RETURNED (Section 13)
      When a returned submission is corrected, is the same submission updated in place
      (new version/revision), or is a new submission created? Is there a resubmission
      count or revision history requirement? Not defined.

A-07  Correcting APPROVED data
      The document defines handling for returned submissions but not for errors found
      AFTER approval, or for corrections needed in a closed period. No amendment or
      re-open process is defined.

A-08  Business rule for who can submit what (Section 14, rule 12; BR-002)
      "Users cannot submit data they are not authorized to submit" and Data Entry has
      "assigned/available datasets". No dataset/period assignment entity or rule is
      defined (no user_dataset_assignment concept in Section 30).

A-09  Permission table asterisks (Section 7)
      - Admin "Enter data / Save draft / Submit data" = YES* conflicts in spirit with
        Section 6.1 ("Admin should not be required to perform ordinary data entry").
        Should Admin be able, but not expected, or should they be excluded?
      - "View analysis" for Data Entry = LIMITED* — what is included in "limited"?
      - "View audit logs" for Reporting = YES* — is this intended (Admin is the stated
        audit log viewer in Section 6.1)?
      - "Enter data" for Admin = YES* and Manager = NO is clear, but the asterisk
        means the permission may change; the business meaning must be fixed.

A-10  Reporting period lifecycle (Section 11)
      Only OPEN and CLOSED statuses are defined. No "upcoming/future" period state,
      no rule for when a period opens, no period lock/grace-period rules, and no rule
      defining what "ordinary new data entry" excludes (e.g., late corrections).

A-11  Multiple users / concurrency
      Can two Data Entry users enter data for the same dataset+period? Who owns the
      draft? What happens if a period is closed while a draft is in progress? Not defined.

A-12  Drafts and dataset/period deactivation
      If a dataset or indicator is deactivated while drafts exist, or a period is closed
      while drafts exist, are existing drafts editable? Submittable? Not defined.

A-13  Custom report structure (Section 18)
      The columns/filters/criteria model is not defined (e.g., is the output a
      indicator-by-period matrix only, or free-form?). Preview-before-export is required,
      but the preview format is not defined.

A-14  "Report History" (Section 17)
      Is the report history a standard report type or a feature (list of previously
      generated reports with who/when/parameters)? Not clearly defined.

A-15  Notifications (Section 26)
      In-system notification architecture is deferred, but it is not defined whether
      notifications are persisted per user, whether they are read/unread, or which
      events trigger them for which roles (e.g., who is notified on submission,
      return, approval).

A-16  Audit coverage (Section 22)
      "Report generation where appropriate" is vague. No retention policy for audit
      logs, no definition of who can delete (should be none), and no requirement for
      immutable storage.

A-17  Password policy / session security (Sections 23–24, 28)
      No minimum password length/complexity, no token expiry, no lockout/rate-limit
      requirement stated.

A-18  Data types and validation specifics (Section 10)
      BOOLEAN/DATE/TEXT validation rules and "configured percentage rules" /
      min/max limits are named but not specified per indicator (e.g., is percentage
      0–100 always or configurable?). Acceptable, but must be fixed at indicator
      design time.

A-19  Reference to source screenshots (Section 4)
      Contains a broken artifact: ":contentReference[oaicite:0]{index=0}".
      The actual reference file is not embedded or path-specified.

5. POTENTIAL REQUIREMENT CONFLICTS
============================================================

K-01  Admin data-entry ability (Section 7 vs Section 6.1)
      Section 7 grants Admin YES* to Enter data/Save draft/Submit data, while Section
      6.1 says Admin "should not be required to perform ordinary data entry".
      Also BR-002/BR-010 give Reporting approval rights, but the permission table
      leaves Admin's review rights as YES, which is consistent; the data-entry asterisk
      is the conflict to resolve.

K-02  Reviewer can approve own data? (Implied)
      Section 6.2 says Data Entry users should not approve their own submitted data,
      and the table grants Approve = YES to Admin and Reporting. However, if Admin can
      also enter data (K-01), an Admin could enter and approve their own data unless a
      separation-of-duties rule is added. BR does not explicitly prohibit self-approval
      for Admin/Reporting entries.

K-03  Submission status naming (Section 13)
      Diagram uses SUBMITTED -> UNDER REVIEW -> APPROVED/RETURNED, and RESUBMITTED ->
      REVIEW -> APPROVED. "REVIEW" and "UNDER REVIEW" appear to be the same step but
      are named differently; RESUBMITTED is not in the status list. This is a naming
      conflict that will confuse state-machine implementation.

K-04  BR-016 vs draft editing (Sections 9, 13, BR table)
      "Inactive datasets cannot accept new submissions" (BR-016) is clear, but it does
      not state whether existing DRAFT submissions for now-inactive datasets can still
      be edited/submitted. Same concern for closed periods (BR-015) vs in-progress
      drafts (see A-12).

K-05  "View audit logs" for Reporting = YES* (Section 7) vs Section 6.1
      Section 6.1 assigns audit-log viewing to Admin; Section 7 gives Reporting YES*.
      If both are true, the audit-log access policy must be clarified.

K-06  Manager dashboard vs Manager data access (Section 6.4, Section 21)
      Manager should view approved data, statistics, and trends. This is consistent
      with BR-014/BR-021, but the document does not explicitly state whether Manager
      can drill into individual submitted (unapproved) values. Table says view analysis
      YES; the boundary between "approved summaries" and "raw unapproved records" is
      not pinned.

K-07  Closed period "ordinary new data entry" wording (Section 11, BR-015)
      "must not accept ordinary new data entry" implies exceptions exist, but no
      exception process (e.g., Admin override, late submission approval) is defined.
      This is a gap rather than a direct contradiction, but it affects BR design.

6. ASSUMPTIONS
============================================================

AS-01  A "submission" groups all indicator values for one dataset and one reporting
       period created by one Data Entry user (proposed, not confirmed).
AS-02  A draft belongs to the Data Entry user who created it and only that user edits it.
AS-03  Returned submissions are corrected by the same Data Entry user who originally
       submitted them (no reassignment workflow is described).
AS-04  Only approved submissions are queryable by Manager-facing analysis/reports.
AS-05  One Reporting user reviews a submission at a time (under review), but the
       document does not forbid multiple reviewers sequentially.
AS-06  Period types beyond monthly are supported by the data model but not required in
       Stage 05; monthly is the primary path.
AS-07  A reporting period, once CLOSED, stays closed; reopening is exceptional and not
       specified.
AS-08  Audit logs are insert-only for ordinary users and cannot be edited through the UI.
AS-09  Dates are stored in a standard format (e.g., ISO) and displayed per hospital locale;
       not specified, so assumed configurable later.
AS-10  The four roles are mutually exclusive per user at a time? Not specified; assumed a
       user has one primary role unless explicitly extended. (NEEDS CONFIRMATION)

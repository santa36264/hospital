============================================================
6. DATASET
============================================================

A Dataset represents a logical group of health indicators that
are collected/reported together.

Examples may include categories such as:

- Monthly Common Dataset
- Maternal/Child Health
- Nutrition
- HIV
- TB
- EPI

These are examples for development/configuration only.

Do NOT claim that these are confirmed datasets of the hospital.

The Admin must be able to create the hospital's actual datasets.

============================================================
7. DATASET ATTRIBUTES
============================================================

A dataset should support at minimum:

id
code
name
description
status
created_at
updated_at

Status:

ACTIVE
INACTIVE

Dataset code must be unique.

Dataset name is required.

Dataset code is required.

Description may be optional.

============================================================
8. DATASET CODE
============================================================

Dataset code:

- required
- unique
- stable
- suitable for API/database references
- should not contain unnecessary whitespace
- should be normalized consistently

Example:

MONTHLY_COMMON

MATERNAL_HEALTH

NUTRITION

The exact codes are configurable by Admin.

Do not hardcode hospital-specific dataset codes into application
logic.

============================================================
9. DATASET STATUS
============================================================

ACTIVE:

The dataset is available for future data-entry operations.

INACTIVE:

The dataset is no longer available for new data-entry operations.

Important:

Deactivation does NOT delete historical data.

Historical submissions and reports must remain preserved.

============================================================
10. DATASET DEACTIVATION RULE
============================================================

When a dataset becomes INACTIVE:

- Existing historical data remains.
- Existing approved submissions remain.
- Existing reports remain possible.
- The dataset must not be available for new data entry.
- The dataset must not be available for new submissions.

Stage 05 must enforce the configuration status.

The actual submission/data-entry enforcement will also be enforced
again in later stages.

============================================================
11. DATASET REACTIVATION
============================================================

An Admin may reactivate an inactive dataset.

ACTIVE
  ↓
INACTIVE
  ↓
ACTIVE

Reactivation does not modify historical data.

============================================================
12. INDICATORS
============================================================

An Indicator represents a specific measurable health-data value
collected within a Dataset.

Example:

Dataset:
Monthly Common Dataset

Indicators might conceptually include:

- Total outpatient visits
- Total admissions
- Total discharges

These are examples only.

Do not present example indicators as confirmed hospital requirements.

The Admin must configure the actual indicators.

============================================================
14. INDICATOR → DATASET RELATIONSHIP
============================================================

Every indicator belongs to exactly one dataset.

Relationship:

Dataset 1
   |
   +---- Indicator A
   +---- Indicator B
   +---- Indicator C

An indicator cannot exist without its dataset.

When an Admin creates an indicator, a valid dataset must be selected.

The backend must verify that the dataset exists.

============================================================
15. INDICATOR CODE
============================================================

Indicator code must:

- be required
- be unique within its dataset
- be normalized consistently
- not contain unnecessary whitespace

The existing Stage 03 database has a uniqueness requirement for:

(dataset_id, code)

Preserve this rule.

Two different datasets may have the same indicator code if the
existing schema allows it.

Within the same dataset, duplicate indicator codes are forbidden.

============================================================
16. INDICATOR NAME
============================================================

Indicator name:

- required
- human-readable
- must not be empty
- should be trimmed

The name is displayed during future data entry and reporting.

============================================================
17. INDICATOR DESCRIPTION
============================================================

Description is optional.

It should explain the meaning of the indicator when necessary.

Example:

"Total number of outpatient visits recorded during the reporting
period."

Do not force descriptions for indicators where they are unnecessary.

19. INTEGER / NUMERIC INDICATORS
============================================================

Numeric indicators may have:

============================================================
20. DECIMAL INDICATORS
============================================================

Decimal indicators may support:

minimum value
maximum value
decimal precision

Example:

decimal precision = 2

The backend must reject values that violate configured
constraints when the indicator is later used for data entry.

Stage 05 primarily stores/configures these rules.

============================================================
21. PERCENTAGE INDICATORS
============================================================

Percentage indicators default to:

0 through 100

unless the indicator configuration explicitly requires another
validated range where supported.

Percentage configuration must be validated.

The Admin UI should make percentage configuration understandable.

Do not allow nonsensical minimum/maximum combinations.

For example:

minimum > maximum

must be rejected.

============================================================
22. TEXT INDICATORS
============================================================

Text indicators store textual information.

They should not use numeric min/max validation as if they were
numeric indicators.

The configuration UI should only display relevant validation
fields for the selected data type.

============================================================
23. DATE INDICATORS
============================================================

Date indicators represent a date value.

Numeric minimum/maximum controls should not be presented as if
they were numeric validation fields.

Use appropriate date configuration only if supported by the
existing requirements/schema.

Do not invent complex date-range requirements.

============================================================
24. BOOLEAN INDICATORS
============================================================

Boolean indicators represent:

TRUE / FALSE

or an equivalent controlled boolean representation.

Do not treat BOOLEAN as arbitrary text.

============================================================
25. REQUIRED INDICATORS
============================================================

Each indicator must support:

required
or
optional

is_required = true/false

Required indicators will later be mandatory during data entry.

Stage 05 configures the rule.

Stage 06 will enforce it during actual data entry.

============================================================
32. MONTHLY PERIOD
============================================================

A monthly period represents one calendar month.

Examples:

January 2026
February 2026
March 2026

The system must store an unambiguous start and end date.

Example:

January 2026:

start_date:
2026-01-01

end_date:
2026-01-31

The implementation must correctly handle:

28-day February
29-day leap-year February
30-day months
31-day months

Do not calculate period dates incorrectly.

============================================================
33. PERIOD STATUS
============================================================

Only:

OPEN
CLOSED

are required.

OPEN:

The reporting period is available for ordinary future data entry.

CLOSED:

The period is locked for ordinary new data entry/submission.

============================================================
34. OPEN PERIOD
============================================================

Admin may open a reporting period.

A period must be valid before it can be opened.

Opening a period does not create submissions automatically.

It simply makes the period available to later data-entry workflows.

============================================================
35. CLOSE PERIOD
============================================================

Admin may close a reporting period.

Once CLOSED:

- New ordinary data entry must not be accepted.
- New ordinary submissions must not be accepted.
- Existing historical data remains.
- Approved data remains.
- Reports can still use approved data.

The exact amendment/correction process for approved data belongs
to a later stage.

============================================================
36. CLOSED PERIOD DRAFT RULE
============================================================

Stage 01 finalized this rule:

If a reporting period is closed while a DRAFT exists:

The draft becomes READ-ONLY.

It cannot be submitted.

Do not delete the draft.

Do not silently modify its values.

Preserve it for historical/accountability purposes.

The detailed data-entry implementation belongs to Stage 06.

Stage 05 must ensure its configuration/API behavior does not
contradict this requirement.

============================================================
37. REOPENING CLOSED PERIODS
============================================================

The Stage 01 project decision is that a closed period remains closed
under ordinary operation.

Reopening is exceptional and must be auditable.

Stage 05 does NOT need to build a general reopen workflow.

If the existing requirements/schema provide a mechanism for
reopening, it must be restricted appropriately and documented.

Do not invent an unrestricted reopen button.

47. DATASET DELETE POLICY
============================================================

There is NO ordinary hard-delete operation for datasets.

Datasets contain indicators and will eventually contain historical
health data.

Therefore:

DELETE dataset
→ not allowed as an ordinary operation

Use:

ACTIVE
INACTIVE

instead.

The UI should not display a normal destructive "Delete Dataset"
action.

============================================================
48. INDICATOR DELETE POLICY
============================================================

Use:

ACTIVE
INACTIVE

instead.

============================================================
49. REPORTING PERIOD DELETE POLICY
============================================================

Do not hard-delete reporting periods that may have associated
submissions or historical records.

The implementation should prevent destructive deletion.

If a newly created unused period requires correction, use controlled
editing according to the implemented validation rules rather than
blind deletion.

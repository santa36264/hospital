5. API ENDPOINTS
============================================================

All require authentication (401) and DATA_ENTRY role (403).

GET    /api/v1/submissions/my
  Returns authenticated user's own submissions.
  Optional query params: status, dataset_id, reporting_period_id.

GET    /api/v1/submissions/:id
  Returns one submission (owner-only, 404 for other users).
  Response: { submission, indicators (ACTIVE only), values map }

POST   /api/v1/submissions
  Body: { dataset_id, reporting_period_id }
  Validates: dataset ACTIVE, period OPEN, no duplicate.
  Returns: created DRAFT submission (201).
  Duplicate returns 409. Invalid dataset/period returns 422.

PATCH  /api/v1/submissions/:id
  Body: { values: [{ indicator_id, value }] }
  Validates: ownership, DRAFT|RETURNED status, period OPEN,
  type/min/max/precision/percentage per indicator (draft = partial OK).
  Upserts data_values, touches updated_at.
  Returns: { submission, indicators, values }

POST   /api/v1/submissions/:id/submit
  Validates: ownership, DRAFT|RETURNED status, period OPEN,
  dataset ACTIVE, all required indicators filled, full type
  and range validation.
  On success: status -> SUBMITTED, submitted_at set.
  History: SUBMITTED or RESUBMITTED (from RETURNED).
  Returns: updated submission.

7. AUTHORIZATION
============================================================

- Anonymous -> 401 on all submission endpoints.
- ADMIN, REPORTING, MANAGER -> 403 on all submission endpoints.
- DATA_ENTRY can only access own submissions (404 for others).
- owner_user_id is always taken from req.user (never trusted
  from request body).
- Status transitions are enforced server-side.

============================================================
8. VALIDATION
============================================================

CREATION
- dataset_id required, dataset must exist and be ACTIVE -> 422
- reporting_period_id required, period must exist and be OPEN -> 422
- Duplicate (dataset_id, reporting_period_id) -> 409

SAVE DRAFT (partial OK)
- Ownership -> 404 (leaks no info about other users)
- Status must be DRAFT or RETURNED -> 409
- Period must be OPEN -> 409
- Invalid typed values rejected (wrong number format, date, etc.)
- Required fields NOT enforced (draft may be incomplete)

SUBMIT (full)
- All of the above
- Dataset must still be ACTIVE -> 409
- All required ACTIVE indicators must have a value -> 422
- Values validated per indicator type and config:
  - numeric: whole number, min/max
  - decimal: number, min/max, precision
  - percentage: 0-100 (or configured range), precision
  - date: valid date string
  - yes/no: yes/no/true/false/1/0
  - text: any non-empty string
- Field-level errors keyed as indicator_{id} -> 422

============================================================
9. TRANSACTION SAFETY
============================================================

createSubmission:
  BEGIN -> INSERT submission -> INSERT history (CREATED)
        -> INSERT audit log -> COMMIT

saveDraft:
  BEGIN -> upsertDataValues (loop) -> UPDATE submission.updated_at
        -> COMMIT

submitSubmission:
  BEGIN -> UPDATE submission status/submitted_at
        -> INSERT history (SUBMITTED|RESUBMITTED)
        -> INSERT audit log -> COMMIT

All transactions use Knex db.transaction(trx => ...).
Repository create/update receive the trx and use it for all
queries including post-operation selects to ensure visibility
within the transaction.

14. PROBLEMS ENCOUNTERED AND FIXED
============================================================

PROBLEM 1: submissionRepository.create / update used `db`
(global connection) instead of `trx` for the post-operation
SELECT. Inside a transaction, the newly inserted row is not
yet visible on the global connection, causing the service
layer to receive `undefined` and throw
"Cannot read properties of undefined (reading 'id')".

FIX: Both create() and update() now use the same connection
(`trx || db`) for the post-operation SELECT, ensuring the
row is always visible within the active transaction.

PROBLEM 2: PowerShell Invoke-RestMethod sends a Content-Type
and body on GET requests when the helper function always
set Body. This caused a ProtocolViolationException.

FIX: Separated ApiGet / ApiPost / ApiPatch helper functions
so GET calls never set a body or ContentType.

PROBLEM 3: PowerShell's Where-Object on a single-item array
returns a scalar (not an array), so .Count returns 1 on the
object itself rather than 0/1 as expected from a filter.

FIX: Wrapped Where-Object output in @() to force array
before calling .Count.

PROBLEM 4: In-memory rate limiter (15 min / 20 req) hit
during repeated test runs. Sessions for some test users
came back null, causing cascading test failures.

FIX: Added 500ms delays between logins; Login() function
made non-throwing on rate-limit errors; 403 checks guard
against null sessions; rate limiter resets on server restart.

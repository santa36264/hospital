============================================================
STAGE 10 — DASHBOARD & DATA ANALYSIS
============================================================

PROJECT:
Hospital Health Data Management, Reporting and Analysis System

============================================================
1. STAGE PURPOSE
============================================================

Implement the Dashboard and Data Analysis layer.

Stage 10 transforms approved health-service data into visual,
management-oriented information.

The dashboard must use APPROVED data only for finalized health
indicators.

The main purpose is to allow authorized management/reporting users
to understand:

- reporting coverage
- approved dataset availability
- indicator values
- period-to-period changes
- trends
- basic comparisons

This stage introduces visualization and analysis.

============================================================
2. IMPORTANT DATA RULE
============================================================

Finalized dashboard and indicator analytics MUST use:

submission.status = APPROVED

ONLY.

Do not use:

DRAFT
SUBMITTED
UNDER_REVIEW
RETURNED

as finalized analytical values.

Submission workflow status may be displayed separately where useful.

Never convert missing data to zero.

============================================================
3. DASHBOARD USERS
============================================================

Stage 10 introduces meaningful MANAGER access.

MANAGER:

- can view management dashboard
- can view approved health indicators
- can view approved trends
- can view approved period comparisons
- cannot edit data
- cannot approve/return submissions
- cannot enter data
- cannot access Admin configuration

REPORTING:

- can access dashboard/analysis
- can continue using reporting features
- can access approved analytical information

ADMIN:

- may access dashboard for system oversight
- retains administrative capabilities

DATA_ENTRY:

- does NOT receive management dashboard/analytics.

Do not weaken existing RBAC.

============================================================
4. DASHBOARD ROUTE
============================================================

Create:

/app/manager

or, if the existing routing architecture is more appropriate:

/app/manager/dashboard

The dashboard must be protected with role authorization.

Only:

MANAGER
REPORTING
ADMIN

may access it.

============================================================
6. DASHBOARD SUMMARY CARDS
============================================================

Provide useful summary metrics.

At minimum:

1. Total Active Datasets

2. Approved Datasets for Selected Period

3. Reporting Coverage

4. Approved Indicators / Available Indicator Data

Do NOT present missing data as zero health measurements.

Reporting Coverage should be calculated as:

approved active datasets / total active datasets × 100

If there are no active datasets:

display:

N/A

rather than 0%.

============================================================
7. PERIOD FILTER
============================================================

Dashboard must allow selecting a reporting period.

Default behavior:

Use the latest available reporting period.

However, do not assume the latest period is APPROVED.

The dashboard must still correctly show approval coverage.

Allow changing the selected period.

============================================================
8. DATASET FILTER
============================================================

Allow:

All Datasets

or

One Dataset

If a dataset is selected:

all relevant dashboard sections should respect that selection.

Do not show indicators from unrelated datasets.

============================================================
9. DATASET REPORTING COVERAGE
============================================================

Display a visual representation of reporting coverage.

Example:

Total Active Datasets: 10

Approved:
8

Not Approved:
2

Coverage:
80%

Possible visualization:

- horizontal progress bar
- donut/pie chart
- simple summary visualization

Use an accessible visual representation.

Do not make the visualization the only way to understand the data.

Show numerical values alongside it.

============================================================
10. DATASET STATUS TABLE
============================================================

Create a dataset status section.

Columns:

Dataset
Code
Selected Period
Status
Approved Date

Statuses:

APPROVED
NOT APPROVED

"NOT APPROVED" means no approved submission exists.

It does NOT mean the health indicator value is zero.

Provide:

View Report

for approved datasets where appropriate.

============================================================
11. KEY INDICATORS
============================================================

Show a useful set of approved indicator values for the selected
period.

At minimum:

- Indicator name
- Dataset
- Value
- Data type
- Period

Only indicators with approved data should be displayed.

Missing values should not appear as zero.

The UI should make clear that these are approved values.

============================================================
12. INDICATOR ANALYSIS
============================================================

Create:

/app/manager/analysis

or an equivalent route consistent with the application architecture.

This page allows users to analyze one indicator over multiple periods.

Selection:

Dataset
Indicator
Start Period
End Period

The indicator dropdown must depend on the selected dataset.

============================================================
13. INDICATOR TREND DATA
============================================================

Display:

- selected indicator
- dataset
- period range
- values by period

Example:

Indicator:
ANC Visits

| Period | Value |
|--------|------:|
| Jan 2026 | 180 |
| Feb 2026 | 195 |
| Mar 2026 | 210 |
| Apr 2026 | 225 |

Only APPROVED values appear as actual values.

If no approved submission exists for a period:

display:

N/A

Do NOT use zero.

============================================================
14. TREND VISUALIZATION
============================================================

Add a chart for numeric/percentage indicators.

Recommended:

Line chart

X-axis:
Reporting Period

Y-axis:
Indicator value

Use an appropriate chart library.

Before installing a library:

inspect package.json.

Prefer a stable React-compatible chart library.

Do not introduce unnecessary dependencies.

For:

INTEGER
NUMERIC
DECIMAL
PERCENTAGE

a line chart may be used.

For:

TEXT
BOOLEAN
DATE

do not force an inappropriate numeric line chart.

Instead display an appropriate table/data representation.

============================================================
15. PERIOD COMPARISON
============================================================

Allow users to compare selected periods.

Example:

Indicator:
HIV Testing Coverage

Current:
81%

Previous:
76%

Difference:
+5 percentage points

For numeric values:

Difference:

current - previous

For percentages:

display percentage-point difference.

Do not incorrectly describe percentage-point change as percentage
growth.

Example:

76% → 81%

Difference:
+5 percentage points

============================================================
16. COMPARISON TABLE
============================================================

Create a comparison table such as:

Indicator
Period A
Period B
Difference

Example:

| Indicator | Aug 2026 | Sep 2026 | Difference |
|-----------|----------|----------|------------|
| ANC Visits | 210 | 245 | +35 |
| Coverage | 76% | 81% | +5 pp |

Only compare compatible numeric/percentage indicators.

For non-numeric indicators:

show the values without mathematical difference.

============================================================
17. MULTI-PERIOD ANALYSIS
============================================================

Allow a reasonable period range.

Example:

Last 6 months
Last 12 months

or:

Start Period
End Period

The backend must determine chronological ordering.

Do not trust frontend period ordering.

============================================================

============================================================

- indicator
- period A value

- calculated difference

============================================================
20. APPROVED DATA QUERY RULE
============================================================

All analytical values must originate from:

data_values
JOIN submissions
WHERE submissions.status = 'APPROVED'

The backend must enforce this.

Never trust a frontend flag such as:

approved=true

to determine whether data is approved.

============================================================
21. ANALYTICS CALCULATION RULES
============================================================

Calculations must happen server-side where practical.

Difference:

current - previous

For percentages:

81 - 76 = +5 percentage points

Do not calculate:

(81 - 76) / 76

unless a future stage explicitly requires growth percentage.

Stage 10 only needs:

absolute difference

and percentage-point difference where applicable.

============================================================
22. MISSING DATA RULE
============================================================

If an approved submission does not exist for a period:

value = null

The UI should display:

N/A

If one period has data and another does not:

Example:

August: 76%
September: N/A

Do not calculate a difference.

Display:

Difference: N/A

============================================================

29. PERFORMANCE
============================================================

Avoid:

- N+1 queries
- fetching all data unnecessarily
- separate queries for every chart point

Use efficient aggregate/query patterns.

The dashboard should load the required data in a reasonable number
of database queries.

============================================================

============================================================

All analytics endpoints require authentication.

Role rules:

MANAGER
REPORTING
ADMIN

may access analytics.

DATA_ENTRY:

403

Anonymous:

401

Do not allow users to bypass RBAC by changing URLs.

============================================================
31. READ-ONLY ANALYTICS
============================================================

Analytics must never modify:

- submissions
- data_values
- submission_history
- audit_logs

Dashboard and analysis endpoints are read-only.

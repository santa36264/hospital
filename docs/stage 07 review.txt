============================================================
1. IMPLEMENTATION SUMMARY
============================================================

Stage 07 implements the complete Reporting review workflow:

- REPORTING users see a live submission queue.
- They explicitly start a review (SUBMITTED -> UNDER_REVIEW).
- They approve (UNDER_REVIEW -> APPROVED) or return
  (UNDER_REVIEW -> RETURNED) with a mandatory reason.
- DATA_ENTRY owners are notified of every status change.
- Return reason is persisted in submission_history and surfaced
  in the DATA_ENTRY submission form.
- All status transitions are atomic (database transactions).
- All workflow events are audit-logged.
- In-app notifications are stored per-user with read/unread
  tracking and a bell badge in the header.

All Stage 03–06 functionality is preserved unchanged.
No Stage 08+ functionality was implemented.

5. API ENDPOINTS (Stage 07 new)
============================================================

REVIEW ENDPOINTS (REPORTING role only — 401/403 otherwise)

GET    /api/v1/review/queue
  Query params: status (SUBMITTED|UNDER_REVIEW), dataset_id,
  reporting_period_id, search.
  Returns submissions with owner details, ordered by submitted_at.

GET    /api/v1/review/submissions/:id
  Returns: { submission (with owner), indicators (all),
             values map, history (with user names) }
  403 if submission is not in a reviewable status.

POST   /api/v1/review/submissions/:id/start
  SUBMITTED -> UNDER_REVIEW.
  409 if not SUBMITTED.
  Writes REVIEW_STARTED history, audit, notifies DATA_ENTRY owner.

POST   /api/v1/review/submissions/:id/approve
  UNDER_REVIEW -> APPROVED.
  409 if not UNDER_REVIEW.
  Writes APPROVED history, audit, notifies DATA_ENTRY owner.

POST   /api/v1/review/submissions/:id/return
  Body: { reason: string (required) }
  UNDER_REVIEW -> RETURNED.
  422 if reason is missing or blank.
  409 if not UNDER_REVIEW.
  Writes RETURNED history (with reason), audit, notifies owner.

NOTIFICATION ENDPOINTS (all authenticated roles)

GET    /api/v1/notifications
  Query: unread=true for unread-only.
  Returns list ordered by created_at desc.

GET    /api/v1/notifications/unread-count
  Returns { count: number }.

PATCH  /api/v1/notifications/:id/read
  Marks one notification read (user-scoped).
  404 if not found or belongs to different user.

PATCH  /api/v1/notifications/read-all
  Marks all user's unread notifications as read.

============================================================
7. AUTHORIZATION
============================================================

- Anonymous -> 401 on all /review and /notification endpoints.
- DATA_ENTRY, ADMIN, MANAGER -> 403 on /review endpoints.
- REPORTING -> 403 on /submissions (DATA_ENTRY creation endpoints).
- Notification endpoints allow any authenticated role (401 if not
  authenticated, otherwise own notifications only).
- reviewer_id is always taken from req.user (never from body).
- Status transitions are validated server-side; no frontend-only
  state changes are trusted.

============================================================
8. VALIDATION
============================================================

START REVIEW
- Must be REPORTING role -> 403 otherwise
- Submission must exist -> 404 otherwise
- Status must be SUBMITTED -> 409 otherwise

APPROVE
- Must be REPORTING role -> 403 otherwise
- Submission must exist -> 404 otherwise
- Status must be UNDER_REVIEW -> 409 otherwise

RETURN
- Must be REPORTING role -> 403 otherwise
- Submission must exist -> 404 otherwise
- Status must be UNDER_REVIEW -> 409 otherwise
- reason required and non-blank -> 422 otherwise

NOTIFICATIONS
- markRead: ownership checked (user_id = recipient_user_id)
  -> 404 if not found or belongs to another user

============================================================
9. TRANSACTION SAFETY
============================================================

startReview:
  BEGIN -> UPDATE status -> INSERT history (REVIEW_STARTED)
        -> INSERT audit -> INSERT notification -> COMMIT

approveSubmission:
  BEGIN -> UPDATE status -> INSERT history (APPROVED)
        -> INSERT audit -> INSERT notification -> COMMIT

returnSubmission:
  BEGIN -> UPDATE status -> INSERT history (RETURNED, reason)
        -> INSERT audit -> INSERT notification -> COMMIT

Notification errors inside transactions are caught and logged
(console.error) but do not abort the main workflow transaction.

============================================================
10. SUBMISSION HISTORY EVENTS (Stage 07)
============================================================

REVIEW_STARTED  — when Reporting starts review
RETURNED        — when Reporting returns (carries reason text)
APPROVED        — when Reporting approves

Combined with Stage 06 events (CREATED, SUBMITTED, RESUBMITTED),
the full lifecycle is now traceable from creation to approval.

============================================================
11. AUDIT EVENTS (Stage 07)
============================================================

SUBMISSION_REVIEW_STARTED  — reviewer, old/new status
SUBMISSION_RETURNED        — reviewer, old/new status, reason
SUBMISSION_APPROVED        — reviewer, old/new status

Uses existing auditLogRepository.log() from Stage 04.

  Recipient: DATA_ENTRY owner

  Recipient: DATA_ENTRY owner
  Message:   "Your submission {dataset} — {period} has been
              approved by {reviewer}."

All notifications are stored in the notifications table.
Delivery is in-app only (no email/SMS — Stage 08+ scope).
Read/unread tracking with read_at timestamp.

15. PROBLEMS ENCOUNTERED AND FIXED
============================================================

PROBLEM 1: API test suite returned 404 on all /review and
/notifications routes despite code being correct.

ROOT CAUSE: The background server process was reused from
Stage 06 (before the new routes were registered). The
`control_pwsh_process` tool returned `isReused: true`.

FIX: Stopped the old process and started a fresh instance.
All 55 tests passed on the fresh server.

PROBLEM 2: (stage 06 carry-over) PowerShell rate limiter
still applies — added 600ms delays between each login call
in test script to avoid hitting the 15-minute rate-limit
window.

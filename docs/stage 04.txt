5. ROLE RESPONSIBILITIES
============================================================

ADMIN

Admin manages the system.

Admin responsibilities include:

- Manage users
- Activate/deactivate user accounts
- Assign the user's primary role
- Manage datasets later
- Manage indicators later
- Manage reporting periods later
- View audit logs

Admin must NOT approve data they personally entered.

REPORTING

Reporting users will later:

- Review submissions
- Start review
- Return submissions with a reason
- Approve submissions
- Generate reports

Stage 04 only implements authenticated identity and authorization.

------------------------------------------------------------

MANAGER

- View approved reports

============================================================
7. PASSWORD SECURITY
============================================================

Passwords MUST NEVER be stored as plaintext.

Use a strong password hashing algorithm suitable for Node.js.

Preferred implementation:

Argon2id

If Argon2id cannot be used reliably in the current Windows
environment, use bcrypt with an appropriate cost factor and
document the reason.

The database must store only the password hash.

Never return:

- password
- password hash
- password reset secrets

through normal API responses.

Initial password requirement:

- minimum 12 characters
- reject empty passwords
- reject passwords that fail the configured password policy

Do not expose password policy details unnecessarily in error
responses.

============================================================
8. JWT AUTHENTICATION DESIGN
============================================================

Use JWT for authenticated sessions.

The JWT must contain only the minimum required claims.

Recommended claims:

- sub — authenticated user ID
- role — primary role
- iat
- exp
- jti where required

Do NOT place sensitive hospital information inside the JWT.

Do NOT place:

- password
- password hash
- health data
- patient data
- confidential business data

inside the token.

============================================================
9. TOKEN STORAGE
============================================================

For the initial implementation, use secure HttpOnly cookies for
JWT/session tokens rather than storing authentication tokens in
localStorage.

The authentication cookie should use appropriate security settings:

- HttpOnly
- Secure in production
- SameSite appropriate for the deployment
- Explicit expiration

The React application must not need to read the JWT directly.

Axios/API requests must send credentials when required.

Express CORS must be configured to allow credentials from the
configured frontend origin.

============================================================
10. ACCESS TOKEN / SESSION EXPIRATION
============================================================

Use a short-lived access JWT.

Initial implementation target:

Access token:
15 minutes

The exact value must be configurable through environment variables.

Do not hardcode the expiration into business logic.

Example:

JWT_ACCESS_EXPIRES_IN=15m

============================================================
11. SESSION / INACTIVITY TIMEOUT
============================================================

Stage 01 requires authenticated sessions to have an inactivity
timeout.

Implement an inactivity timeout.

Initial implementation target:

30 minutes of inactivity.

The timeout must be configurable.

Example:

SESSION_INACTIVITY_TIMEOUT_MINUTES=30

The system must not silently keep an inactive session alive
indefinitely.

A request from an expired/inactive session must require
reauthentication or a valid refresh/session mechanism.

============================================================
12. REFRESH SESSION
============================================================

Implement a refresh mechanism suitable for the JWT architecture.

Recommended approach:

- Short-lived access JWT
- Longer-lived refresh/session token
- Refresh token stored in HttpOnly cookie
- Refresh token rotation
- Server-side refresh/session record where necessary
- Logout invalidates the active refresh session

The refresh mechanism must not expose refresh tokens to normal
React JavaScript.

Recommended initial refresh lifetime:

7 days

Make the value configurable.

Example:

JWT_REFRESH_EXPIRES_IN=7d

============================================================
13. LOGOUT
============================================================

Implement:

POST /api/v1/auth/logout

Logout must:

1. Invalidate the active refresh/session token where applicable.
2. Clear authentication cookies.
3. Prevent the same refresh session from being reused.

Do not treat merely deleting a frontend variable as logout.

The backend must participate in logout.

============================================================
14. AUTHENTICATION ENDPOINTS
============================================================

Implement these endpoints:

POST /api/v1/auth/login

POST /api/v1/auth/logout

POST /api/v1/auth/refresh

GET /api/v1/auth/me

The endpoint responsibilities are:

------------------------------------------------------------

POST /api/v1/auth/login

Input:

email/username
password

Successful result:

authenticated user session

Must not return password information.

------------------------------------------------------------

POST /api/v1/auth/logout

Terminates the current authenticated session.

------------------------------------------------------------

POST /api/v1/auth/refresh

Creates a new valid access token/session from a valid refresh
session.

Invalid, expired, revoked, or reused refresh tokens must be
rejected.

------------------------------------------------------------

GET /api/v1/auth/me

Returns the currently authenticated user's safe account information.

Example conceptual response:

{
    "success": true,
    "message": "Authenticated user retrieved successfully.",
    "data": {
        "id": "...",
        "name": "...",
        "email": "...",
        "role": "DATA_ENTRY",
        "status": "ACTIVE"
    }
}

Do not expose sensitive fields.

============================================================
15. LOGIN VALIDATION
============================================================

Login must validate:

- Required email/username
- Required password
- Correct credential format where applicable

Authentication failures should return a generic message.

Do not reveal whether:

- The account exists
- The password was wrong
- The account exists but another credential was wrong

in a way that creates unnecessary account enumeration.

============================================================
16. ACCOUNT STATUS
============================================================

Users have an account status.

Initial statuses:

ACTIVE
INACTIVE

Only ACTIVE users may authenticate.

An INACTIVE user attempting login must not receive an authenticated
session.

Administrators will manage account status in a later
administration stage.

Stage 04 only needs the authentication layer to enforce status.

============================================================
17. AUTHENTICATION MIDDLEWARE
============================================================

Create backend authentication middleware.

Responsibilities:

1. Read authentication credentials.
2. Validate authentication token/session.
3. Verify token signature.
4. Verify expiration.
5. Verify session validity where applicable.
6. Resolve the authenticated user.
7. Verify the user is still ACTIVE.
8. Attach authenticated user information to the request.

Conceptually:

request.user

must be available to protected controllers after successful
authentication.

Unauthenticated requests must be rejected.

============================================================
18. ROLE AUTHORIZATION MIDDLEWARE
============================================================

Create reusable backend role authorization middleware.

Example conceptual usage:

requireRole('ADMIN')

requireRole('REPORTING')

requireRole('MANAGER')

requireRole('DATA_ENTRY')

The backend must enforce authorization independently from React.

Example:

A Manager calling an Admin-only endpoint directly through Postman
must receive an authorization error.

Hiding the button in React is NOT security.

30. 401 HANDLING
============================================================

When the backend returns:

401 Unauthorized

the client should:

1. Attempt an appropriate refresh when the session can be refreshed.
2. If refresh fails, clear authentication state.
3. Redirect the user to /login.

Do not create infinite refresh loops.

Do not retry requests indefinitely.

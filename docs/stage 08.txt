============================================================
STAGE 08 — DATASET REPORTS & REPORT MANAGEMENT
============================================================

PROJECT:
Hospital Health Data Management, Reporting and Analysis System

============================================================
1. STAGE PURPOSE
============================================================

Implement the first reporting layer of the system.

Stage 08 allows authorized users to view structured reports from
APPROVED submissions only.

The purpose is to transform validated and approved health data into
useful reports without modifying the underlying submission workflow.

Reporting must be based on approved data.

IMPORTANT:

The system is for ONE HOSPITAL.

Do not introduce:
- multi-hospital hierarchy
- facility hierarchy
- woreda/zone/region reporting
- external facility management

============================================================
2. REPORTING PRINCIPLE
============================================================

Only:

submission.status = APPROVED

may be used as finalized reporting data.

DRAFT:
- excluded

SUBMITTED:
- excluded

UNDER_REVIEW:
- excluded

RETURNED:
- excluded

APPROVED:
- included

Reports must never modify:
- submissions
- data_values
- submission_history

Reports are read-only.

============================================================
3. REPORT TYPES — STAGE 08
============================================================

Implement these report types:

A. Dataset Report
B. Monthly Report
C. Indicator Report
D. Submission Status Report
E. Report History

Do NOT implement Stage 09 functionality yet:

- Custom Report
- custom indicator-by-period builder
- PDF export
- Excel export
- advanced custom filtering
- advanced period comparison
- trend analysis

============================================================
4. DATASET REPORT
============================================================

Purpose:

Show approved indicator values for one selected dataset and
reporting period.

Example:

Dataset:
Monthly Common Dataset

Period:
September 2026

Display:

Dataset information:
- Dataset name
- Dataset code
- Reporting period
- Period type
- Submission status
- Submitted by
- Approved date

Indicator table:

| Indicator | Code | Type | Value |
|----------|------|------|-------|

For each indicator belonging to the dataset:

- indicator name
- indicator code
- data type
- submitted value

Use the approved submission.

If an indicator has no value:

display an appropriate empty/Not Available state.

Do not silently invent or calculate values.

============================================================
5. MONTHLY REPORT
============================================================

Purpose:

Provide a monthly overview of approved datasets.

User selects:

- Reporting Period

The system displays datasets with approved submissions for that
period.

Example:

September 2026

| Dataset | Code | Submitted By | Approved Date | Status |
|---------|------|--------------|---------------|--------|

Only APPROVED submissions are treated as finalized.

If a dataset has no approved submission:

display:

Not Approved / No Approved Submission

Do not treat missing data as zero.

============================================================
6. INDICATOR REPORT
============================================================

Purpose:

Allow a user to select:

- Dataset
- Indicator
- Reporting Period

Then display the approved value.

Example:

Dataset:
PMTCT

Indicator:
Number of HIV-positive pregnant women

Period:
September 2026

Display:

Indicator information:
- Indicator name
- Indicator code
- Dataset
- Data type
- Reporting period
- Value

If the selected submission is not APPROVED:

do not present the value as finalized.

Show an appropriate status message instead.

============================================================

Purpose:

Filters:

- Reporting Period
- Dataset
- Status

Statuses:

DRAFT
SUBMITTED
UNDER_REVIEW
RETURNED
APPROVED

- Dataset
- Reporting Period

- Status

- Approved date

This is a workflow report.

============================================================
8. REPORT HISTORY
============================================================

Create a read-only report history page showing previously viewed
report requests.

Important:

Do not create a complicated report-versioning system in Stage 08.

Report History should record basic report access information such as:

- user
- report type
- dataset if applicable
- reporting period if applicable
- accessed/generated timestamp

Use the existing audit infrastructure where appropriate OR create
a minimal dedicated report history mechanism only if required.

Do not implement document/file storage for reports.

============================================================
9. REPORT ACCESS
============================================================

Stage 08 report access:

REPORTING:
- can access reporting pages
- can view reports
- can view submission status reports
- can view approved data

MANAGER:
- may access finalized approved reports where appropriate
- manager dashboard/analytics is NOT implemented yet

DATA_ENTRY:
- does NOT receive management/reporting analytics
- continues to access own submission workflow

ADMIN:
- do not automatically give Admin reporting functionality unless
  explicitly required by the existing role rules.

Follow the existing RBAC architecture.

Do not weaken existing authorization.

============================================================
10. REPORT API DESIGN
============================================================

Use:

/api/v1/reports

Suggested endpoints:

GET /api/v1/reports/dataset

Query parameters:

dataset_id
reporting_period_id

Returns the approved submission and its indicator values.

------------------------------------------------------------

GET /api/v1/reports/monthly

Query parameters:

reporting_period_id

Returns approved dataset summaries for the selected period.

------------------------------------------------------------

GET /api/v1/reports/indicator

Query parameters:

dataset_id
indicator_id
reporting_period_id

Returns the approved indicator value and metadata.

------------------------------------------------------------

GET /api/v1/reports/submission-status

Query parameters:

reporting_period_id
dataset_id
status

Returns submission workflow status information.

------------------------------------------------------------

GET /api/v1/reports/history

Returns report access history for the authenticated user,
according to authorization rules.

============================================================
12. REPORT QUERY RULES
============================================================

Report queries must enforce:

1. Only approved submissions are used for finalized reports.

2. The submission must belong to the selected dataset.

3. The submission must belong to the selected reporting period.

4. Indicator must belong to the selected dataset.

5. Indicator must be active OR historically valid according to the
existing database design.

Do not allow an indicator from Dataset A to be queried against
Dataset B.

6. Do not trust frontend filtering for authorization.

7. Validate IDs and query parameters server-side.

============================================================
13. DATA INTEGRITY
============================================================

The report layer must not change submission data.

No report endpoint may:

- create submission
- update submission
- update data_values
- approve submission
- return submission
- change workflow status

Reports are READ ONLY.

============================================================
25. SECURITY
============================================================

All report endpoints require authentication.

Apply role authorization according to Stage 08 access rules.

Never trust:

- dataset_id from frontend
- indicator_id from frontend
- reporting_period_id from frontend

without server-side validation.

Prevent unauthorized access to report data.

Do not expose sensitive internal database details in API errors.

============================================================
26. PERFORMANCE
============================================================

Use efficient queries.

Avoid:

- N+1 queries
- loading all submissions unnecessarily
- loading all indicators repeatedly

Use joins/aggregations where appropriate.

Only fetch the data required by each report.

Pagination should be used for report history and large status lists.

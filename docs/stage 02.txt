3. ARCHITECTURAL PRINCIPLES
============================================================

The application must follow these principles:

1. Separation of concerns.
2. Clear frontend/backend separation.
3. REST API communication.
4. Server-side authorization.
5. Server-side validation.
6. Business logic must not be placed directly inside routes.
7. Database access must be separated from HTTP handling.
8. Sensitive configuration must use environment variables.
9. Authentication and authorization must be centralized.
10. Errors must be handled consistently.
11. API responses must follow a consistent structure.
12. The system must be maintainable and testable.
13. Future stages must not unnecessarily rewrite previous stages.
14. Business requirements must not be silently changed.
15. Security must be enforced on the backend even when the frontend
    also performs validation.

4. HIGH-LEVEL SYSTEM ARCHITECTURE
============================================================

The system consists of the following major layers.

------------------------------------------------------------
4.1 PRESENTATION LAYER
------------------------------------------------------------

Technology:

React

Responsibilities:

- User interface
- Forms
- Tables
- Dashboards
- Charts
- Navigation
- Client-side validation
- Loading states
- Error states
- Notifications
- Authentication state
- Role-based interface visibility

The React client communicates with the backend only through the
REST API.

The client must not contain database credentials.

------------------------------------------------------------
4.2 API LAYER
------------------------------------------------------------

Technology:

Node.js + Express.js

Responsibilities:

- HTTP requests
- API routing
- Authentication middleware
- Authorization middleware
- Request validation
- Controller execution
- Error handling
- Response formatting

Routes should remain thin.

Business logic should not be implemented directly inside route files.

------------------------------------------------------------
4.3 BUSINESS LOGIC LAYER
------------------------------------------------------------

The backend should contain a service layer.

Responsibilities:

- Business rules
- Submission workflow
- Dataset rules
- Indicator validation
- Reporting logic
- Approval/return logic
- Notification creation
- Report generation logic
- Data analysis calculations
- Authorization-sensitive business operations

Controllers should call services instead of containing large amounts
of business logic.

------------------------------------------------------------
4.4 DATA ACCESS LAYER
------------------------------------------------------------

Responsibilities:

- Database queries
- CRUD operations
- Transactions
- Query composition
- Data retrieval

Database-access logic should be separated from controllers.

The implementation must use parameterized queries or a secure ORM/
query builder approach to prevent SQL injection.

The exact MySQL access library may be selected during Stage 03 after
considering the project architecture.

------------------------------------------------------------
4.5 DATABASE LAYER
------------------------------------------------------------

Technology:

MySQL

Responsibilities:

- Persistent data storage
- Relationships
- Constraints
- Indexes
- Transactional integrity
- User data
- Dataset configuration
- Indicators
- Reporting periods
- Submissions
- Data values
- Revision history
- Notifications
- Audit logs

The exact schema is NOT finalized in Stage 02.

The detailed schema will be designed in Stage 03.

8. CONTROLLER RESPONSIBILITIES
============================================================

Controllers are responsible for handling HTTP concerns.

A controller may:

- Receive request.
- Extract parameters.
- Call validation.
- Call a service.
- Return an API response.

Controllers should NOT contain large business rules.

Bad conceptual design:

Route
  ->
Controller
  ->
hundreds of lines of database queries and business rules


Preferred:

Route
  ->
Middleware
  ->
Controller
  ->
Service
  ->
Repository
  ->
Database

18. AUTHORIZATION ARCHITECTURE
============================================================

Authentication answers:

"Who is the user?"

Authorization answers:

"What is this user allowed to do?"

The backend must enforce role/permission checks.

Example:

Admin
  -> user management

Data Entry
  -> draft/data submission workflow

Reporting
  -> review/approval/reporting

Manager
  -> approved data/analysis


Frontend route protection alone is NOT sufficient.

Each user has ONE primary role in the initial version:

ADMIN
DATA_ENTRY
REPORTING
MANAGER

Multi-role users are out of scope for the initial version.

Every protected API operation must enforce authorization on the
server.

38. BUSINESS LOGIC BOUNDARIES
============================================================

The following rules must be enforced on the server:

- Only authorized users can perform protected actions.
- Only Data Entry users use ordinary data-entry workflow.
- A Data Entry user owns their draft.
- Only one active submission exists for Dataset + Period.
- Submitted data cannot be freely edited.
- Reporting starts review.
- Reporting can return or approve.
- Return requires a reason.
- Returned data can be corrected and resubmitted.
- Approved data cannot be directly edited by Data Entry.
- Approved amendments must be controlled and auditable.
- Closed periods cannot accept ordinary new entry.
- Inactive datasets cannot accept new entry.
- Inactive indicators cannot accept new values.
- Manager-facing reports use approved data.
- Audit logs cannot be edited/deleted by ordinary users.
- Audit-log endpoints are Admin-only in the initial version.
- Data Entry cannot approve submissions.
- A user cannot approve data they personally entered.
- Admin does not perform ordinary data entry.
- Frontend restrictions are not sufficient for separation of duties;
  backend authorization/business rules must enforce this.

============================================================
39. API SECURITY BOUNDARY
============================================================

Every protected API endpoint must determine:

1. Is the user authenticated?
2. Is the user's account active?
3. What role does the user have?
4. Does the role have permission?
5. Does the user own or have access to the resource?
6. Is the requested business operation valid?
7. Is the resource in a valid state?

Example:

A Data Entry user attempting:

POST /api/v1/submissions/123/approve

must be rejected even if the user manually sends the request.

Frontend hiding the button is not sufficient.

============================================================
40. FRONTEND SECURITY BOUNDARY
============================================================

The frontend improves usability but is not trusted for security.

Frontend responsibilities:

- Hide unauthorized navigation.
- Protect routes.
- Show appropriate UI.
- Perform user-friendly validation.
- Display API errors.

Backend responsibilities:

- Authentication
- Authorization
- Validation
- Business rules
- Resource ownership
- Database integrity

44. ARCHITECTURAL QUALITY REQUIREMENTS
============================================================

The implementation should avoid:

- Giant controllers.
- Giant React components.
- Duplicate business logic.
- Direct database access from React.
- Hardcoded credentials.
- Hardcoded API URLs.
- Business rules implemented only in frontend.
- Repeated authorization logic.
- Unnecessary global state.
- Unnecessary dependencies.
- Mixing unrelated modules.
- Silent changes to requirements.

The implementation should favor:

- Small focused modules.
- Reusable services.
- Centralized error handling.
- Centralized API communication.
- Clear validation.
- Clear authorization.
- Consistent responses.
- Testable business logic.

45. STAGE 02 ARCHITECTURAL DECISIONS
============================================================

The following decisions are fixed for the project:

AD-01
React is the frontend.

AD-02
Node.js + Express.js is the backend.

AD-03
MySQL is the database.

AD-04
React communicates with Express through REST API.

AD-05
React never connects directly to MySQL.

AD-06
Backend follows Route -> Middleware -> Controller -> Service ->
Repository/Data Access -> Database architecture.

AD-07
Business logic belongs primarily in services.

AD-08
Database access is separated from controllers.

AD-09
Authentication uses JWT.

AD-10
Authorization is enforced on the backend.

AD-11
The API base version is /api/v1.

AD-12
The backend uses centralized error handling.

AD-13
API responses follow a consistent structure.

AD-14
Sensitive configuration uses environment variables.

AD-15
The system uses role-based access control.

AD-16
The frontend uses role-aware routing/navigation.

AD-17
Approved data is the source for official reporting and analysis.

AD-18
Important workflow operations are auditable.

AD-19
Notifications are persisted in the database.

AD-20
The detailed MySQL schema belongs to Stage 03.

AD-21
Application implementation belongs to later stages.

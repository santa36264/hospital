PROJECT:
Hospital Health Data Management, Reporting and Analysis System


============================================================
1. STAGE PURPOSE
============================================================

Implement the Reporting workflow for submitted health-data
submissions.

Stage 07 adds:

SUBMITTED
    ↓
UNDER_REVIEW
    ↓
APPROVED

or

UNDER_REVIEW
    ↓
RETURNED
    ↓
DATA_ENTRY CORRECTION
    ↓
SUBMITTED

The Reporting role is responsible for reviewing submissions.

The stage must include both:

1. Backend workflow/business rules
2. Complete usable Reporting UI/UX

============================================================
4. ROLES
============================================================

ADMIN
- Existing administrative configuration responsibilities.

DATA_ENTRY
- Creates and submits data.
- Corrects RETURNED submissions.
- Cannot review/approve.

REPORTING
- Reviews SUBMITTED submissions.
- Starts review.
- Checks data quality.
- Approves valid submissions.
- Returns invalid submissions with a mandatory reason.

MANAGER
- Consumes approved data later.
- No approval functionality in this stage.

============================================================
8. START REVIEW
============================================================

Endpoint:

POST
/api/v1/submissions/:id/review/start

Rules:

- REPORTING only.
- Submission must exist.
- Submission must currently be SUBMITTED.
- Change status:

SUBMITTED → UNDER_REVIEW

- Set appropriate review timestamp.
- Record submission history.
- Record audit event.

If already UNDER_REVIEW:

Return controlled conflict or allow continue-review behavior
according to the established workflow.

Do not allow DATA_ENTRY to call this endpoint.

============================================================
10. DATA QUALITY REVIEW
============================================================

Reporting must be able to inspect:

- Indicator name
- Indicator type
- Entered value
- Required status
- Min/max configuration
- Precision configuration where applicable

Highlight validation/data-quality problems clearly.

Do not silently modify submitted values.

Reporting is reviewing submitted data, not editing the
DATA_ENTRY user's values directly.


============================================================
11. APPROVE
============================================================

Endpoint:

POST
/api/v1/submissions/:id/approve

Rules:

- REPORTING only.
- Submission must be UNDER_REVIEW.
- Approve the submission.
- Status:

UNDER_REVIEW → APPROVED

- Set approved timestamp.
- Record submission history.
- Record audit event.

Approved submissions become permanently read-only through
ordinary workflow.

Return clear success response.


============================================================
12. RETURN FOR CORRECTION
============================================================

Endpoint:

POST
/api/v1/submissions/:id/return

Rules:

- REPORTING only.
- Submission must be UNDER_REVIEW.
- A return reason is mandatory.
- Status:

UNDER_REVIEW → RETURNED

- Store return reason.
- Set returned timestamp.
- Record submission history.
- Record audit event.

Do not allow an empty return reason.


============================================================
13. RETURN REASON
============================================================

The return reason must be visible to DATA_ENTRY.

Example:

"Female and male OPD totals do not match total OPD visits.
Please verify the reported figures."

The reason must be stored in the database.

If the existing submissions table has a suitable return/review
reason field, reuse it.

Only create a migration if the existing schema is insufficient.


============================================================
14. DATA ENTRY RETURNED WORKFLOW
============================================================

Stage 06 already supports:

RETURNED + OPEN period

as editable.

Stage 07 must integrate with that existing behavior.

After Reporting returns:

UNDER_REVIEW → RETURNED

DATA_ENTRY can:

1. Open submission.
2. Read return reason.
3. Correct values.
4. Save.
5. Submit again.

Then:

RETURNED → SUBMITTED

The DATA_ENTRY user must not be able to directly change
RETURNED → APPROVED.

============================================================

+

Anonymous:
401

Wrong role:
403

DATA_ENTRY cannot review.

MANAGER cannot review.

Admin has broad configuration privileges.


============================================================
20. REPORTING DATA ACCESS
============================================================

Reporting may view submissions required for review.

Reporting must NOT:

- modify indicator values directly
- change submitted values
- approve its own data entry
- bypass workflow states
- create arbitrary APPROVED submissions
- directly set status through request body

Status transitions must be controlled by dedicated operations.


============================================================
21. WORKFLOW STATE MACHINE
============================================================

Allowed:

SUBMITTED → UNDER_REVIEW

UNDER_REVIEW → APPROVED

UNDER_REVIEW → RETURNED

RETURNED → SUBMITTED

Not allowed:

SUBMITTED → APPROVED

SUBMITTED → RETURNED

DRAFT → APPROVED

DRAFT → UNDER_REVIEW

RETURNED → APPROVED

APPROVED → anything

DATA_ENTRY cannot perform Reporting transitions.


============================================================
22. PERIOD RULES
============================================================

Reporting review must consider the reporting period state.

If a period is CLOSED:

Existing submitted data may still be reviewed and approved.

Closing a period must NOT automatically destroy or invalidate
existing submissions.

Do not allow DATA_ENTRY to modify a returned submission if
the period is CLOSED.

Existing Stage 06 behavior remains authoritative for
DATA_ENTRY editing.


============================================================
23. TRANSACTION SAFETY
============================================================

Review state changes must use database transactions.

Example approve:

BEGIN

verify current status
update submission
record submission history
record audit event
create notification

COMMIT

On failure:

ROLLBACK


============================================================
24. CONCURRENCY / STATE SAFETY
============================================================

Do not blindly update status.

Example:

If two Reporting users attempt to start review simultaneously,
only a valid current-state transition may succeed.

The service must verify the current state before transition.

Return a controlled conflict when the transition is no longer
valid.
